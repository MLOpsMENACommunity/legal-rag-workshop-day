Opening · press → to step through

Why reading a few answers misses failures

  • → 1: you read 3 answers by eye. All look fine.
  • → 2: the eval scores all 20 the same way and finds 4 failures, including the three from the previous slide.
  • → 3: the maths. With 4 bad answers in 20, three random reads miss every one of them about half the time: C(16,3) ÷ C(20,3) = 560 ÷ 1140 ≈ 49%.
  • Line to land: "a demo is a sample of three."
Why evaluate · press → to step through

Three jobs people mix up

  • Exam. → 1: you take one golden question and ask the system: it retrieves articles, the LLM writes, the answer comes out.
  • → 2: compare it with the reference answer; the judge scores it onto the scoreboard.
  • → 3: repeat for all 20, get averages, decide: below the floor means fix before release. It stops a bad release, not a bad answer.
  • → 4: dashcam. Real users, traces of each step, a dashboard; the alert rings after the damage is done.
  • → 5: brakes. One answer carrying a national ID hits the guardrail and is redacted before it leaves. It stops this one answer.
  • → 6: three jobs, three moments. None replaces the others.
Why evaluate

There is no universal LLM metric

TaskWhat failure looks likeSo you measure
Chatbotrude, unhelpful, off-topichelpfulness, tone, safety
Summarizerdrops key points, adds factscoverage, consistency with the source
Legal RAG oursinvented ruling · wrong or phantom article · repealed law treated as live · half the needed articles · worse in Arabicfaithfulness · citation accuracy · context recall · repeal & refusal behaviour · AR/EN parity
Start from how your system fails, then pick metrics that drop when it does. Never the other way round.
  • BLEU/ROUGE, "LLM score out of 10": generic metrics measure something, just not your risk.
  • For a lawyer, a fluent answer citing the wrong article is worse than "I don't know".
Why evaluate · press → to step through

Where a RAG system breaks

  • On entry: one question takes the happy path.
  • → 1 parsing: the parser glues Art. 147 and 148 into one record, so retrieval can never return 147 alone (W1's job).
  • → 2 retrieval: the question is embedded next to the wrong article.
  • → 3 ranking: the right article is 9th; top_k = 5 cuts it before the LLM sees it.
  • → 4 generation: the LLM adds a clause that is in no article.
  • → 5 citation: it cites an article it never retrieved.
  • → 6: retrieval failures are measured with code (we know the right article numbers); generation failures need a judge.
The golden set · press → to step through

The golden set: the exam every version must sit

  • → 1: 10 questions from the reference benchmark. → 2: lawyers write and approve 4.
  • → 3: an LLM drafts 6; a human rejects 2. Unchecked synthetic questions only test whether one LLM agrees with another.
  • → 4: 2 real questions that failed in production (W5 closes this loop). 20 total.
  • → 5: version it (DVC); two runs on the same version are comparable.
  • → 6: edit one question and the hash changes: run C cannot be compared with A or B.
  • Room activity if time allows: each participant writes 2 questions of their own.

Pitfalls

  • Too easy: questions copied from the article text. BM25 wins, nothing is tested.
  • Rot: W1 re-parses and article numbers shift. Gold IDs silently go stale.
  • Unversioned: someone edits a question, and last week's scores are no longer comparable.
  • English only: hides the Arabic gap.
  • Size: 20 in the room, 50 take-home, a few hundred before you trust small differences.
  • The seed set (code/data/golden_set.seed.jsonl) is exactly this mix: 10 AR/EN pairs.
  • With 20 questions one question is 5 percentage points. Don't celebrate a 0.03 improvement.
  • Version it with DVC; the runner logs its hash with every run.
What to measure · press → to step through

Four arrows, four questions

  • On entry the pipeline produces the three things we can judge: question, retrieved articles, answer.
  • Each → a judge compares one pair: precision (question vs articles), faithfulness (articles vs answer), relevancy (answer vs question).
  • → 4: recall needs a fourth thing, the reference answer a lawyer wrote once; it compares reference vs articles.
  • → 5: faithfulness 1.0 and recall 0.0 at the same time: faithful and still wrong.

Judging answers · press → to step through

The green side needs a judge: another LLM

  • A judge is just a prompt template plus a model plus a parser.
  • → 1: the three inputs fill the template's slots. → 2: the filled prompt goes to the judge model.
  • → 3: it answers in JSON: claims, a 1/0 verdict per claim, a reason.
  • → 4: code turns the verdicts into a number (1 ÷ 2 = 0.5) and logs it per question.
  • RAGAS is a library of carefully written versions of exactly this.
Judging answers · press → to step through

A judge is an instrument, and it has biases

Log the judge model as an MLflow parameter: a new judge means new scores.
  • Four small experiments; ask the room to predict each result before you press.
  • → 1 verbosity: same facts, the padded answer scores higher. → 2 self-preference: identical answers, the one from the judge's own family wins.
  • → 3 language: the same answer in Arabic scores lower. → 4 noise: one input, three different scores.
  • Calibration and bias tests are take-home; know they exist.
Judging answers · press → to step through

Faithfulness, step by step

  • → 1: the judge LLM splits the answer into atomic claims (one LLM call).
  • → 2: each claim is checked against the retrieved text (more LLM calls). c1 and c2 are backed by Article 147; c3 is not in any sentence.
  • → 3: score = supported ÷ all = 2/3. c3 sounds like real law, which is exactly why fluent hallucinations are dangerous.
  • Note: faithfulness never looks at the reference answer, only at what was retrieved.
Judging answers · press → to step through

Answer relevancy: does it answer the question?

  • The judge reads only the answer and writes 3 questions that answer would answer. Each is embedded; the score is the mean cosine with the real question.
  • Good answer: the generated questions point the same way as the real one, ≈ 0.97.
  • Pasted article: everything in it is true, but the questions it answers are different ones, ≈ 0.35.
  • Use a multilingual embedding model (we use BAAI/bge-m3), or Arabic answers score low for the wrong reason.
Judging answers · press → to step through

Context precision: is the useful stuff on top?

  • → 1: the judge marks each retrieved article useful or not, against the reference answer.
  • → 2: precision is computed at every useful rank, then averaged: (1/3 + 2/5) ÷ 2 = 0.37.
  • → 3: a reranker moves the same two articles to the top: 1.00. Same retrieval, better order. This is what W2's reranker is for.
Judging answers · press → to step through

Context recall: did we retrieve everything needed?

Precision and recall need a reference answer. Faithfulness and relevancy do not, so those two can also run on live traffic in W5.

  • Recall starts from the reference, not the answer: split it into claims and look for each in what was retrieved.
  • Only "good faith" (Art. 148) is found: 1/3. Retrieving Art. 147 as well makes it 3/3.
  • This is the metric that catches "faithful and still wrong".

Arabic · the corpus's biggest asset · press → to step through

Same question, two languages, same article?

  • This test answers a question almost nobody measures: does your embedding model understand Arabic, or just match characters?
  • Why it is free: every article exists in Arabic and English, so every golden question gets a twin, linked by pair_id.
  • Watch the judge too: an English-centric judge scoring Arabic answers may be biased. Hand-check a sample.
  • Normalisation from W2 (normalize_arabic_for_sparse) shows up here: turn it off and watch the gap grow.
  • Code: bilingual.py, 30 lines.
The code · press → to step through

A module, not a notebook

  • This is literally what python -m evaluation run does.
  • → 1: runner.py asks the API every golden question; each row gets the answer and the article numbers it used.
  • → 2: free scorers fill hit@5 and citation columns. → 3: the judge fills faithfulness, one paid call per cell.
  • → 4: column means → report.json → one MLflow run. → 5: the gate compares with the floors: exit 1, the PR cannot merge (W5 wires this).
  • The reference repo evaluates in notebooks; a notebook can't be a CI gate.

Experiments · press → to step through

Every evaluation is an MLflow run

  • Each run: set the config knobs, run the eval, and a run card (params, metrics, artifacts, tags) lands in the experiment table.
  • → 1 baseline, → 2 512-token chunks, → 3 dense only. Change one knob at a time.
  • → 4: compare. 512-token chunks drop hit@5 because chunks no longer map to articles: W1's design, justified by numbers.
  • In the room: each table runs one configuration.
Experiments · click a column to sort · illustrative numbers, replace with the room's runs

Did W1 and W2 choose right?

  • These numbers are illustrative, shaped like real results. Replace them with the room's runs (edit the RUNS array in the deck).
  • 512-token chunks: faithfulness looks fine, citation_correct collapses. Chunks no longer map to articles, which is W1's "chunk by article" argument in numbers.
  • top_k 20: recall up, precision and cost down. Every metric is a trade-off; pick the one that matches your risk.
Thresholds · why 0.75 in CI and 0.80 for alerts?

A threshold has to survive the judge's noise

Floor = baseline − measured noise. Run one config 3× to measure σ. Plus a regression rule: fail if a metric drops > 0.05 vs main.

  • Each dot is one CI run of the same PR: 20 questions, noisy judge.
  • Set true quality to 0.80 and noise 0.05: the gate at 0.75 still fails some runs of a good PR. Flaky gates get disabled, and a disabled gate is no gate.
  • 0.80 alert in production watches a rolling average over many requests: lower noise, so it can be tighter and fire before the release floor is reached.
Wrap-up · press → to step through

Evaluation is a loop, not a step

  • Follow one change: lower top_k → eval → compare with main → gate passes → ship and observe.
  • A user asks about the repealed Art. 60 and gets a wrong answer in a trace: that becomes golden question 21.
  • The exam keeps growing, so the system can't quietly regress. Hand-off to W4 and W5.
Wrap-up · press → for each

Five things to keep

  • Eyeballing is not evaluation. A fixed golden set, scored the same way every time.
  • Split retrieval from generation. Retrieval metrics are free: run them on every commit.
  • Code before judges. Citations, repeal and refusals are deterministic checks.
  • Judges are instruments. Log them, calibrate them, and distrust them on Arabic until checked.
  • Every change is a run; every PR passes the gate.

Done when

  • golden set ≥ 20 questions, Arabic and English
  • all four RAGAS metrics computed and logged
  • ≥ 3 MLflow runs with different configurations
  • bilingual result written in the report
  • evaluation lives in src/, not a notebook

Take-home: run the full 50, run one config 3× to measure noise, hand-check 20 judgments against a lawyer, add 5 adversarial questions.
