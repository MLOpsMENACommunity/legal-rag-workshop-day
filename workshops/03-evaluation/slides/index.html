Why evaluate · press → to add each job

Three jobs people mix up

  • Evaluation: fixed questions, before release, produces scores. It stops a bad release, not a bad answer.
  • Observability: real traffic, after release. Tells you afterwards.
  • Guardrails: inline, every request. The only one that blocks one bad answer.
  • Common mistake: "we have Langfuse, so we evaluate." No: traces without a fixed exam cannot tell you if v2 is better than v1.
Why evaluate

There is no universal LLM metric

TaskWhat failure looks likeSo you measure
Chatbotrude, unhelpful, off-topichelpfulness, tone, safety
Summarizerdrops key points, adds factscoverage, consistency with the source
Legal RAG oursinvented ruling · wrong or phantom article · repealed law treated as live · half the needed articles · worse in Arabicfaithfulness · citation accuracy · context recall · repeal & refusal behaviour · AR/EN parity
Start from how your system fails, then pick metrics that drop when it does. Never the other way round.
  • BLEU/ROUGE, "LLM score out of 10": generic metrics measure something, just not your risk.
  • For a lawyer, a fluent answer citing the wrong article is worse than "I don't know".
Why evaluate · press → for each failure

Where a RAG system breaks

  • Walk left to right. 1 is W1's job (parsing). 2–3 are retrieval. 4–5 are generation.
  • Retrieval failures can be measured with plain code because we know the gold article numbers. Generation failures need a judge.
  • The question to always ask about a wrong answer: did it retrieve the right article? If no, fix retrieval. If yes, fix the prompt/model.

Pitfalls

  • Too easy: questions copied from the article text. BM25 wins, nothing is tested.
  • Rot: W1 re-parses and article numbers shift. Gold IDs silently go stale.
  • Unversioned: someone edits a question, and last week's scores are no longer comparable.
  • English only: hides the Arabic gap.
  • Size: 20 in the room, 50 take-home, a few hundred before you trust small differences.
  • The seed set (code/data/golden_set.seed.jsonl) is exactly this mix: 10 AR/EN pairs.
  • With 20 questions one question is 5 percentage points. Don't celebrate a 0.03 improvement.
  • Version it with DVC; the runner logs its hash with every run.

Judging answers · press → to step

Faithfulness, step by step

Retrieved context · Article 147

The contract makes the law of the parties. It may only be revoked or amended by mutual agreement or for reasons provided by law. (2) If exceptional, unforeseeable public events make performance excessively onerous, the judge may reduce the obligation to a reasonable limit.

Answer under test

Under Article 147 a contract binds both parties and can only be changed by mutual agreement. A judge may reduce an onerous obligation after exceptional events, and must cancel the contract if one party lost more than a third of its value.

1 · the judge splits the answer into claims
c1A contract binds both parties and changes need mutual agreement.
c2A judge may reduce an onerous obligation after exceptional events.
c3The judge must cancel the contract if a party lost over a third of its value.
2 · each claim is checked against the context
2 / 3 = 0.67 supported claims ÷ all claims.
c3 was invented: the exact failure that matters most in law.
  • Step 1: decomposition into atomic claims (an LLM call). Step 2: NLI-style verification of each claim against the retrieved text (more LLM calls). Score = ratio.
  • c3 sounds like real law (it resembles a lesion rule) but is not in Article 147. That's why fluent hallucinations are dangerous.
  • Cost: at least 2 judge calls per question just for this metric.

Answer relevancy

Answer relevancy

  1. Judge writes 3 questions the answer would answer
  2. Embed them and the real question
  3. Mean cosine similarity

Drops when it pastes the whole article, hedges, or answers a neighbouring question.

judges the retriever
⌖

Context precision

Is what we retrieved actually useful?

flip for the recipe ↻

Context precision

  1. For each retrieved article: is it useful for the reference answer?
  2. Average precision, weighted by rank

Drops when ten articles come back and one is useful, or the useful one sits at rank 9.

judges the retriever
∑

Context recall

Did we retrieve everything the answer needs?

flip for the recipe ↻

Context recall

  1. Split the reference answer into claims
  2. Can each be attributed to the retrieved articles?
  3. Fraction attributed

Drops when the answer needs three articles and we found one.

Context precision and recall need a reference answer. Faithfulness and relevancy do not, which is why they can also run on live traffic in W5.
  • Answer relevancy needs an embedding model: use a multilingual one (we use BAAI/bge-m3) or Arabic answers score low for the wrong reason.
  • Retrieval-side RAGAS metrics are LLM versions of what we computed for free on slide 11. With gold IDs, prefer the free ones; RAGAS versions help when gold IDs are missing.

Thresholds · why 0.75 in CI and 0.80 for alerts?

A threshold has to survive the judge's noise

Floor = baseline − measured noise. Run one config 3× to measure σ. Plus a regression rule: fail if a metric drops > 0.05 vs main.

  • Each dot is one CI run of the same PR: 20 questions, noisy judge.
  • Set true quality to 0.80 and noise 0.05: the gate at 0.75 still fails some runs of a good PR. Flaky gates get disabled, and a disabled gate is no gate.
  • 0.80 alert in production watches a rolling average over many requests: lower noise, so it can be tighter and fire before the release floor is reached.
Wrap-up · press → to go round

Evaluation is a loop, not a step

  • Every change gets measured. Every failure in production becomes a new golden question. The set grows; the system can't silently regress.
  • Hand-off to W4: "you'll re-run this after every optimisation." And W5: "you'll wire the gate into CI."
Wrap-up · press → for each

Five things to keep

  • Eyeballing is not evaluation. A fixed golden set, scored the same way every time.
  • Split retrieval from generation. Retrieval metrics are free: run them on every commit.
  • Code before judges. Citations, repeal and refusals are deterministic checks.
  • Judges are instruments. Log them, calibrate them, and distrust them on Arabic until checked.
  • Every change is a run; every PR passes the gate.

Done when

  • golden set ≥ 20 questions, Arabic and English
  • all four RAGAS metrics computed and logged
  • ≥ 3 MLflow runs with different configurations
  • bilingual result written in the report
  • evaluation lives in src/, not a notebook

Take-home: run the full 50, run one config 3× to measure noise, hand-check 20 judgments against a lawyer, add 5 adversarial questions.
